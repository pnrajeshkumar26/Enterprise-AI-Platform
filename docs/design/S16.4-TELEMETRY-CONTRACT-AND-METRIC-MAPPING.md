## 1. Scope and design rules

This document covers the current Runtime API Prometheus metrics, evaluation metrics, existing Prometheus scrape jobs, the current Grafana dashboard references, and the proposed telemetry needed by later workflow, RAG, MCP and agent phases.

Rules:

1. Reuse existing metrics when their meaning matches the requirement; do not create duplicate counters for the same event.
2. Use counters for cumulative events, gauges for current/latest values, and histograms for distributions such as latency and iteration count.
3. Keep labels bounded and controlled. Never use trace IDs, span IDs, session IDs, user IDs, raw prompts, document IDs, arbitrary tool arguments or exception text as Prometheus labels.
4. Keep trace and span IDs in traces and sanitized logs, not metric labels.
5. Keep technical workflow outcome separate from AI answer-quality outcome.
6. Treat self-hosted inference cost as an estimate, not an actual cloud invoice or provider-billed amount.
7. Add new metric instrumentation in the phase that introduces the corresponding component. This contract defines names and semantics; it does not claim those future metrics already exist.

## 3. Contract for future components

The following metrics are **proposed**, not yet implemented. Add them alongside their owning component and test them with success and failure paths.

| Metric | Type | Allowed labels | Definition |
|---|---|---|---|
| `ai_workflow_runs_total` | Counter | `workflow`, `environment`, `outcome`, `release` | One increment when a workflow reaches exactly one terminal outcome. |
| `ai_workflow_duration_seconds` | Histogram | `workflow`, `environment` | Wall-clock time from workflow start to terminal state. |
| `ai_workflow_timeouts_total` | Counter | `workflow`, `timeout_category` | Explicit workflow/operation deadlines exceeded. |
| `ai_agent_invocations_total` | Counter | `agent`, `environment`, `outcome` | One increment per attempted agent invocation. |
| `ai_agent_duration_seconds` | Histogram | `agent`, `environment` | Agent invocation duration. |
| `ai_agent_iterations` | Histogram | `agent`, `workflow` | Number of iterations used by an invocation. |
| `ai_tool_calls_total` | Counter | `tool`, `server`, `outcome` | One increment per tool call attempt. |
| `ai_tool_duration_seconds` | Histogram | `tool`, `server` | Tool execution duration. |
| `ai_rag_retrieval_duration_seconds` | Histogram | `retrieval_pipeline`, `environment` | Retrieval pipeline duration. |
| `ai_rag_retrieval_results` | Histogram | `retrieval_pipeline`, `environment` | Number of results returned per retrieval. |
| `ai_rag_ingestion_total` | Counter | `source_type`, `outcome` | Document ingestion terminal outcomes; no document ID label. |
| `ai_guardrail_events_total` | Counter | `guardrail_type`, `outcome` | Policy/guardrail decisions. |
| `ai_approval_requests_total` | Counter | `approval_type`, `outcome` | Approval request outcomes. |
| `ai_workflow_estimated_cost_usd_total` | Counter | `workflow`, `cost_category` | Estimated allocated workflow cost; document the estimation source. |

### 3.1 Terminal workflow outcomes

Use one and only one terminal outcome for each accepted workflow run:

- `completed`: defined technical workflow completed.
- `failed`: an unhandled technical error prevented completion.
- `timed_out`: an explicit workflow or operation deadline expired.
- `cancelled`: execution was intentionally cancelled.
- `rejected`: validation or policy prevented execution before work began.
- `partial`: use only when the product explicitly supports returning partial evidence as a terminal result.

Record AI quality separately, for example in evaluation results. An HTTP 200 or a technically completed workflow does not prove the answer is correct or safe.

### 3.2 Label policy

Allowed label values must be bounded configuration enums or controlled registries. Examples: known workflow names, configured agent roles, registered tool names, deployment environment, release identifier and defined outcome enums.

Never use these as labels: trace/span IDs, session or user IDs, prompt text, document/chunk IDs, arbitrary URLs, exception messages, free-form tool inputs or outputs, API keys, or other sensitive values.

Use trace/span context in OTEL traces and sanitized logs to correlate individual executions.

## 4. Derived measures and denominator rules

| Measure | Definition | Important rule |
|---|---|---|
| Generation failure rate | `increase(llm_generation_failures_total[window]) / increase(llm_requests_total[window])` | Filter to matching model/status scope; guard against zero denominator. Confirm whether failure counter and request status count the same event before publishing. |
| Workflow timeout rate | timed-out eligible workflow runs / eligible workflow runs started | Define whether rejected runs are included; default: exclude pre-execution rejections and report them separately. |
| Agent failure rate | failed agent invocations / attempted agent invocations | Count one terminal outcome per invocation. |
| Evaluation pass rate (event-based) | `increase(evaluation_pass_total[window]) / increase(evaluation_requests_total[window])` | Only valid for the same label scope and a counter set that records all completed evaluations. |
| Cost per completed workflow | estimated attributed workflow cost / completed workflows | Label as estimate; state which cost categories are included. |
| Cost per quality-passing task | estimated attributed cost / tasks passing the defined quality and safety gate | Evaluation population and gate version must be recorded. |

Do not use a rate formula against a Gauge snapshot. For report-derived `evaluation_pass_rate`, display the latest report value directly; do not apply `rate()` or `increase()`.
