**Branch:** `feature/enterprise-agentic-platform`

## 1. Purpose and scope

This register records the main security, privacy, operational and financial risks for the Enterprise AI Platform Operations Copilot. It is a living engineering register, not a penetration-test report, formal compliance certification or proof that all controls are already implemented.

The initial platform includes FastAPI/model serving, evaluation, Prometheus/Grafana, and the local Alloy/Loki/Tempo lab. Planned phases add workflows, RAG/Qdrant, MCP tools, single-agent and multi-agent execution, evaluation/governance controls and operational dashboards.

### Security principles

1. Default to read-only operational access.
2. Enforce authorization at the tool/server boundary, not only in the UI or agent prompt.
3. Treat prompts, retrieved documents, tool outputs and model responses as untrusted data.
4. Use explicit schemas, allowlists, bounded inputs/outputs, deadlines and execution budgets.
5. Never expose arbitrary shell, unrestricted filesystem access, or direct production mutation to an agent.
6. Redact sensitive values before logging; keep secrets out of source code, metrics, traces and prompts.
7. Apply least privilege, access control, retention and audit to logs, traces, vector data and workflow state.
8. Separate local-lab convenience settings from production security requirements.

## 2. Qualitative risk method

Likelihood and impact use Low / Medium / High / Critical. The initial rating is a qualitative engineering estimate based on the planned architecture and current lab configuration; it must be reassessed when deployment exposure, data classification and threat evidence change.

| Impact | Meaning |
|---|---|
| Low | Limited inconvenience; easy recovery; no sensitive data or material service impact. |
| Medium | Local service degradation, limited data exposure or recoverable cost impact. |
| High | Significant sensitive-data exposure, platform compromise, sustained outage or material spend. |
| Critical | Privileged control-plane compromise, broad confidential-data exposure or unsafe production action. |

Treat High/Critical impact risks as requiring explicit mitigations and validation before the related feature is exposed beyond the isolated lab.

## 4. Trust boundaries and minimum policy

| Boundary | Data crossing the boundary | Minimum policy |
|---|---|---|
| User/UI → FastAPI | Request text, identity/context | Validate input; authenticate/authorize; size/rate limits; do not trust client-provided role claims without verification. |
| FastAPI/workflow → model | Prompt, retrieved evidence, tool results | Remove secrets; separate instructions from untrusted evidence; constrain output; apply model/time/token budgets. |
| RAG → workflow | Document chunks, metadata, citations | Source provenance, access filters, content treated as untrusted, citation references preserved. |
| MCP client → MCP server/tool | Tool name and structured arguments | Explicit allowlist, schema validation, server-side authorization, timeout, output cap, audit. |
| Agent → another agent | Task, evidence and intermediate state | Typed handoff; least-privilege context; bounded delegation; independent verification for consequential claims. |
| Application → logs/traces/metrics | Operational metadata and diagnostic events | Redaction before export; bounded labels; restricted access; retention and deletion policy. |
| Services → storage | Workflow state, vectors, telemetry | Access control, encryption where supported, backups, retention, tenant/session isolation. |

### Initial prohibited capabilities

- Arbitrary shell or command execution by agents.
- Unrestricted filesystem browsing or file write tools.
- General-purpose network browsing/proxy tools with no domain allowlist.
- Direct production configuration changes, restarts, deployment, deletion or remediation.
- Storing API keys, passwords, access tokens, raw secrets or unrestricted prompt payloads in logs, traces, metric labels or source control.

Any future state-changing action requires an explicit authorization model, human approval, audit event, idempotency/replay policy, rollback plan and dedicated tests before enablement.

## 5. Observability-specific security baseline

Current local lab facts reviewed:

- Alloy discovers Docker containers and reads Runtime API container stdout/stderr through the Docker socket.
- Loki is configured with `auth_enabled: false` and a local filesystem store.
- Loki retention is configured for 72 hours.
- Grafana, Prometheus, Tempo, Loki and Alloy are intended for isolated local development; local ports are bound to loopback where configured.

Required guardrails:

1. Keep this configuration isolated to the developer workstation; do not publish these endpoints to a public or shared network.
2. Docker socket mounting is privileged even when the socket bind mount is marked read-only; that flag does not make Docker API operations read-only.
3. Before shared/cloud deployment, design authenticated access, TLS, RBAC, secret handling, network policies and hardened log collection.
4. Define log redaction and trace sampling before collecting sensitive production payloads.
5. Add collector health, export failure, dropped telemetry and storage-pressure monitoring.

## 6. Resource and cost model

### 6.1 Cost categories

| Cost category | Cost driver / calculation | Current planning treatment |
|---|---|---|
| Local developer workstation | Incremental CPU/RAM/disk/electricity and Docker overhead | Existing workstation; record resource use for integrated runs. No monetary rate assumed. |
| Runtime API/model serving | Host/instance hours, CPU/RAM, GPU/VRAM, model process uptime | Reuse existing local/CPU paths for application tests; use GPU only for measured model behaviour. |
| GPU experiments | `instance hourly rate × billable hours + attached storage + data transfer/tax` | Scheduled sessions; start/stop and verify all billable resources. |
| Hosted model APIs (if used) | `input tokens / 1M × input rate + output tokens / 1M × output rate` | Optional only; use current provider rate card at time of experiment. |
| Workflow/agents | Model tokens + tool calls + persistence/compute + retries | Enforce per-run time, token, iteration and tool-call budgets. |
| RAG/Qdrant | Vector count, vector dimensions, index/metadata size, RAM, disk, backups | Start with a small representative corpus; benchmark before sizing. |
| Embeddings | `embedded tokens / 1M × embedding rate` or measured local compute | Compare hosted cost with local CPU/GPU inference; do not assume one is free. |
| Logs/traces | Daily ingest × retention + index/compaction overhead + storage/egress | Loki/Tempo local storage for lab; measure ingestion before extending retention. |
| Cloud storage (future) | GB-month + requests + retrieval + egress + replication | S3 is a future option, not part of the current local implementation. |
| Evaluation | Candidate and judge model tokens, execution time, report storage | Use deterministic/local tests by default; schedule judge/GPU runs. |

### 6.2 Storage sizing formulas

Use measurements rather than guessed capacity:

- Daily raw log volume (GB/day) ≈ average ingest rate (MB/s) × 86,400 ÷ 1,024.
- Retained raw log volume ≈ daily log volume × retention days.
- Add measured index, compaction, trace and filesystem headroom separately; do not assume compression ratios without observing them.
- For vectors, estimate `vector count × dimensions × bytes per element`, then add measured index, metadata and replication overhead.

The current Loki 72-hour retention setting is a lab default, not a production retention decision.

### 6.3 Budget controls

- Default to CPU and mocked adapters for unit tests, orchestration, retrieval plumbing and security tests.
- Rent/enable GPU only for a planned, measured experiment; stop/terminate immediately after the session.
- Check instance, attached disk, snapshots, IPs and other billable resources after shutdown.
- Set a per-experiment budget and a monthly ceiling before launch.
- Enforce workflow limits: maximum wall-clock duration, agent iterations, tool calls, model tokens and retries.
- Report estimated self-hosted compute cost separately from provider-billed model cost and actual cloud invoice totals.
- Include storage, snapshots, data transfer, taxes and idle resources in cloud cost review.

**Provisional envelope from the architecture draft:** 5–10 GPU hours/month and a suggested initial ceiling of USD 15–20/month for GPU-related experiments. This is a planning proposal only, not an approved budget or a price guarantee. Confirm the provider's current rates, storage/network charges and currency/tax treatment before any paid run.

### 6.4 Unit economics to add when workflow telemetry exists

- Cost per completed workflow = attributed estimated cost / completed workflows.
- Cost per quality-passing task = attributed estimated cost / tasks passing the defined quality and safety gate.
- Tool cost per workflow = allocated tool/provider charges / completed workflows.
- GPU utilization efficiency = useful measured workload time / billable GPU time.

Every report must state which cost components are included and whether the result is estimated or invoice-backed.
